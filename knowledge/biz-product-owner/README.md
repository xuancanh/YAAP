# Product Owner knowledge base

Your playbooks tell you to write specs, break them into stories, refine the backlog and accept delivered work. These docs cover how to do each so engineering builds the right thing the first time and acceptance is a quick check rather than a debate.

Ordering methods (RICE and similar) are in the shared prioritisation topic; estimation is in the shared planning topic. These docs stay on the Product Owner's craft.

## Which doc to use

| When you are… | Open |
|---|---|
| Writing or reviewing a product spec | [Spec template and review checklist](spec-template.md) |
| Splitting a spec into stories that fit a sprint | [Slicing stories](story-slicing.md) |
| Writing acceptance criteria, or accepting delivered work | [Acceptance criteria guide](acceptance-criteria.md) |
| Refining the backlog, deciding if an item is ready, answering questions mid-sprint | [Backlog readiness](backlog-readiness.md) |
| Reporting readiness, spec rework or accepted versus committed | [Product Owner metrics](product-owner-metrics.md) |

## Principles

1. **Problem before solution.** A spec that starts with the feature has skipped the part engineering most needs: why.
2. **Thin slices of value.** Each story should leave the user able to do something new, however small.
3. **Testable or it isn't done.** If you cannot say how you would check a criterion, rewrite it.
4. **Answer fast.** A question from engineering that waits a day costs a day. Clear your questions queue first each morning.
5. **No promises outside.** Dates and scope commitments to customers go through the Head of Product.
