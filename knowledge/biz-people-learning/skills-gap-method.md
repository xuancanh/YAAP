# Skills gap method

A gap analysis is useful when it ends in a short ranked list of gaps, each tied to a key result, with the right fix chosen. Training is only one of the fixes.

## 1. Map capabilities to objectives

For each objective and key result, ask the function lead: "What must the team be able to do, that they do repeatedly, to hit this?" Write each capability as a verb phrase that can be observed.

- Weak: "Data literacy."
- Strong: "Builds a weekly funnel report from the analytics export without help and explains week-on-week changes."

Keep the map to the capabilities that matter this cycle. A full competency framework is a different project.

## 2. Rate current capability with evidence

Use a simple scale per capability per team:

| Level | Meaning |
|---|---|
| 0 | Not needed yet / not applicable |
| 1 | Can't do it without someone else doing most of it |
| 2 | Can do it with guidance or review |
| 3 | Does it reliably without help |
| 4 | Does it well and can teach others |

Base each rating on evidence, and note the source:
- performance-cycle themes (aggregated);
- manager input against the scale;
- recurring review comments in accepted tasks (e.g. the same correction keeps coming back);
- onboarding feedback;
- incidents or rework that trace to the capability.

Record the **needed** level next to the **current** level. The gap is the difference.

## 3. Check it's really a skills gap

Before recommending training, ask:

- **Do people know what's expected?** If not, it's a clarity problem; fix the brief, goal or standard.
- **Do they have the tools, data and access?** If not, fix those.
- **Could they do it if their life depended on it?** If yes, it's not a skill gap; look at time, incentives, process or priorities.
- **Is the process itself broken?** Training people to work around a bad process wastes everyone's time.
- **Is it a few people or most?** One or two people may need coaching; most of a team suggests a process or onboarding fix too.

Record what you concluded. Many gaps end up as "playbook" or "process change", which is a good outcome.

## 4. Rank the gaps

Score each gap on two things, using whatever scale the team prefers (1–3 is enough):

- **Impact:** how much closing it would move a key result. High if the key result is at risk and this is a main cause.
- **Reach:** how many people it affects.

> **Priority score** = impact × reach

Then adjust for urgency (a deadline, a launch, an audit) and for effort, and say why you adjusted. Ties go to the gap with the clearest link to a key result.

## 5. Recommend a fix per top gap

| Fix | When it fits |
|---|---|
| **Playbook or guide** | The method exists but isn't written down; people need a reference at the moment of work |
| **Practice with feedback** | People know the theory but need reps (writing, reviews, difficult conversations) |
| **Workshop** | A shared method the whole team should use the same way |
| **Coaching or mentoring** | One or a few people, or a judgment skill learned by example |
| **Process or tool change** | The gap is really in the system |
| **Hiring** | The capability is needed at a level that can't be built in time; for the Head of People to raise |

## Output format

Top three to five gaps, one row each:

| Capability | Key result | Teams | Current → needed | Evidence | Real cause | Priority | Recommended fix |
|---|---|---|---|---|---|---|---|

Then one paragraph on what you deliberately left out and why.

## Pitfalls

- Asking people what training they want and calling it a gap analysis. Preferences are useful input, not evidence of a gap.
- Rating individuals in shared files. Rate teams, keep individual data in the HR system.
- Listing twenty gaps. Nobody can act on twenty.
- Assuming that more senior people don't have gaps (manager skills are often the biggest one).
