# Program Coordinator knowledge base

You keep cross-functional programs on a written plan and make lateness visible early. Your playbooks set the artefacts: charter, RAID log, weekly status, retro. These docs make each artefact good enough that people act on it.

You coordinate across units through the board and backlog. Work in another unit becomes a backlog task for its lead; you do not assign it.

## Which doc to use

| When you are… | Open |
|---|---|
| Starting a program and writing its charter | [Charter template](charter-template.md) |
| Building the milestone plan or working out what is on the critical path | [Milestones and the critical path](milestones-and-critical-path.md) |
| Adding or reviewing RAID rows | [Writing a useful RAID log](raid-log-guide.md) |
| Writing the Thursday status | [Status report template](status-report-template.md) |
| Reporting on milestones on time and RAID ownership | [Coordinator metrics](coordinator-metrics.md) |

## Principles

1. **Written beats remembered.** If a date, owner or decision is not in the charter, plan or RAID log, assume nobody agreed it.
2. **Late is information.** Report a slip the week you see it. Hiding it for a week only removes a week of options.
3. **Every row has an owner and a date.** An issue with no owner is the most important line in the status.
4. **Ask, don't assign.** Across units you request and follow up; the unit lead decides.
